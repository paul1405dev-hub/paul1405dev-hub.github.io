Pygame 종스크롤 슈팅 게임 과제의 네 번째 기능(F4, 피격과 게임 오버)을 구현하기 전에 설계 결정을 정리한 문서다. 구조는 뱅크샐러드 테크 스펙 양식(요약, 배경, 목표, 목표가 아닌 것, 계획, 이외 고려 사항, 마일스톤)을 따랐다. 앞 기능은 [F1 플레이어 이동]({{ site.baseurl }}/2026-11-17-oss-proj1-f1-tech-spec/), [F2 총알 발사]({{ site.baseurl }}/2026-11-17-oss-proj1-f2-tech-spec/), [F3 적 명중과 점수]({{ site.baseurl }}/2026-11-18-oss-proj1-f3-tech-spec/) 테크 스펙에 있다.

## 요약

- 플레이어가 총알로 처리하지 못한 적에 대한 처리. 이 경우 생명이 줄고, 0이 되면 게임 오버.
- 생명을 잃는 두 경우(플레이어에 닿음, 화면 아래로 지나감)를 책임별 메서드로 나누고 하나의 상위 메서드로 묶는다. 게임 오버 판정은 그 밖에서 따로 한다.
- 설계 결정 5개를 구현 전에 정하고, 구현은 `feature/gameover` 브랜치에서 커밋 2개로 나눈다.

## 배경

- F3까지로 총알이 적을 잡고 점수가 오르지만, 적이 플레이어에게 닿아도 지나가도 아무 일도 없다. F4는 생명이 줄어드는 규칙과 게임 오버를 만드는 기능이다. F5(재시작·최고 점수)가 `end_game()`과 `draw_game_over()`를 이어서 쓴다.
- F3과 F4가 `update`를 함께 건드려서 F4 브랜치는 F3을 머지한 `main`에서 만들었다.
- 이번 과제의 개인 목표는 코드를 많이 쓰는 것보다 구현 전에 설계 선택지와 트레이드오프를 직접 파악하고 선택하는 것이다.

## 목표

- 적이 플레이어에 닿으면 그 적을 없애고 생명(`self.lives`)을 1 줄인다. 닿지 않고 화면 아래로 지나간 적도 생명을 1 줄인다.
- 생명이 0 이하가 되면 `self.end_game()`을 실행한다.
- 게임 오버 화면에 가운데 `GAME OVER`와 이번 판 점수를 표시한다. 게임 오버 뒤에는 적이 더 움직이거나 나타나지 않는다.

## 목표가 아닌 것

- R 키 재시작, 최고 점수 저장·표시, `Press R to restart` 안내는 F5의 범위다.
- 무적 시간, 피격 효과음·깜빡임, 목숨 추가 아이템처럼 과제에 없는 기능은 다루지 않는다.

## 계획

### 1. 현재 구조 분석

| 대상 | 위치 | 알게 된 것 |
|---|---|---|
| 판정 자리 | `main.py` `update()` | 총알 처리(F3) 다음에 F4 TODO 세 곳(플레이어에 닿음, 아래로 지나감, 생명 0 이하)이 이 순서로 있다. 지나간 적을 `kill()`하는 반복문은 이미 있고 생명 감소만 비어 있다 |
| 생명 | `main.py` `reset()` | `self.lives`가 `START_LIVES`(3)로 만들어진다. HUD가 오른쪽 위에 `LIVES`로 이미 그린다 |
| `spritecollide` | pygame | 그룹과 그룹의 비교가 아니라 단일 스프라이트와 그룹을 비교한다. `dokill`이 True면 그룹 쪽 스프라이트만 `kill()`하고 기준 스프라이트는 지워지지 않는다. 돌려주는 값은 부딪힌 그룹 쪽 스프라이트의 리스트다 |
| 게임 오버 처리 | `main.py` `end_game()` | `self.game_over = True`로 바꾼다. 호출만 하면 된다 |
| 게임 오버 이후 | `main.py` `update()`, `handle_events()` | `update()`가 맨 먼저 `return`하고, `handle_events()`가 `not self.game_over`로 적 생성을 막는다. 그래서 적이 더 움직이거나 나타나지 않게 하는 일은 스타터가 이미 처리하고 있다 |
| 게임 오버 화면 | `main.py` `draw_game_over()` | `self.game_over`가 True일 때 `draw()`가 부른다. 본문이 `pass`다. 글자를 그리는 `draw_text`, 큰 글꼴 `big_font`, 작은 글꼴 `font`, 색 상수가 이미 있다 |

### 2. 목표 구조

★은 F4에서 작성하는 부분이다.

```
update()                                   (main.py)
 ├─ handle_bullet_hits()                   F3
 ├─ handle_life_loss() ★                   생명을 잃는 경우를 묶은 상위 메서드
 │    ├─ handle_player_hits() ★            플레이어에 닿은 적 처리
 │    ├─ handle_passed_enemies() ★         화면 아래로 지나간 적 처리
 │    └─ 생명을 0 이상으로 고정
 └─ check_game_over() ★                    생명이 0 이하면 end_game()

draw()
 └─ draw_game_over() ★                     GAME OVER(큰 글꼴, 노랑), 점수(작은 글꼴, 흰색)
```

### 3. 설계 결정과 트레이드오프

#### 결정 1. 플레이어와 적의 충돌을 어떻게 찾을 것인가

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `spritecollide(self.player, self.enemies, True)` | 과제 힌트이고 한 줄이다. 돌려받은 리스트의 길이가 닿은 적의 수다 | `player`가 한 스프라이트여서 F3의 `groupcollide`와 모양이 다르다 |
| B. 플레이어를 그룹에 넣어 `groupcollide` | F3과 같은 함수로 통일된다 | 플레이어만 담긴 그룹을 새로 만들어야 하고 돌려주는 값이 사전이다 |
| C. 적마다 `player.rect.colliderect(enemy.rect)` 직접 비교 | 판정 원리가 보인다 | 반복문과 삭제, 닿은 수 세기를 직접 써야 한다 |

**선택: A.** 과제 힌트인 `spritecollide`를 쓴다. `groupcollide`로 하려면 플레이어만 담긴 그룹을 새로 만들어야 하는데, 플레이어는 지우지 않을 거라(`dokill` False) 그 추가 구조가 필요 없다.

#### 결정 2. 생명 감소와 게임 오버 판정을 어떻게 구성할 것인가 (구조 설계)

개념: **단일 책임**과 **중복**(같은 규칙이 두 곳에 있으면 한쪽만 고치다 어긋난다). 생명이 줄어드는 곳이 두 군데다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. TODO 세 곳에 각각 직접 쓴다 | 과제 모양 그대로다 | `self.lives -= 1`이 두 곳에 있고 `update`가 길어진다 |
| B. 책임별 메서드로 나눈다 | `update`는 흐름만 읽힌다. F3의 `handle_bullet_hits`와 같은 방식이다 | 메서드가 셋이 되고 생명 감소는 여전히 두 곳이다 |
| C. 생명을 깎는 일을 메서드 하나에 모은다 | 생명이 줄면 이렇게 한다는 규칙이 한곳에 있다 | 이름과 호출이 한 단계 더 늘고 TODO 세 자리와 모양이 달라진다 |

**선택: B.** 책임별로 나누는 기준을 F1~F3과 같이 유지한다. 플레이어에 닿은 적 처리, 화면 아래로 지나간 적 처리, 게임 오버 판정을 각각 메서드로 둔다. 두 처리는 판정이 달라서 한 메서드에 합치지 않고 따로 둔다.

하위 결정으로 생명을 잃는 두 경우를 하나의 상위 메서드로 묶어서 `update`가 한 번 부른다. 생명을 잃는 경우를 한곳에 묶어 관리하면 게임을 더 발전시킬 때 관리하기 편해 보여서다. 게임 오버 판정은 그 묶음 밖에 두고 묶음 호출 다음에 따로 부른다. 묶음은 생명을 깎는 일만 맡고, 게임 오버는 생명이 0 이하인가라는 별도 규칙으로 남긴다.

#### 결정 3. 게임 오버 검사를 언제 할 것인가

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `update` 끝에서 한 번 검사 | 과제 TODO 위치 그대로다. 한 프레임에 생명이 여러 번 줄어도 `end_game()`은 한 번만 불린다 | 생명이 0이 된 프레임이 끝날 때까지 남은 코드가 한 번 더 실행된다 |
| B. 생명을 깎는 순간마다 검사 | 0이 되는 즉시 게임 오버다 | 한 프레임에 두 번 깎이면 `end_game()`이 두 번 불릴 수 있다. F5가 `end_game()`에서 최고 점수를 저장하면 저장도 두 번이다 |

**선택: A.** 결정 2에서 정한 구조(게임 오버 판정이 생명을 잃는 경우 처리 묶음 밖에서 따로 불린다)와 이어진다.

#### 결정 4. 게임 오버 화면을 어떻게 그릴 것인가 (구조 설계)

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `draw_text`를 줄마다 직접 호출 | 코드가 가장 단순하다 | F5에서 줄이 늘면 y 좌표를 줄마다 직접 맞춰야 한다 |
| B. 줄을 목록으로 만들어 반복하며 간격으로 위치를 계산 | F5에서 줄만 목록에 더하면 된다. 시작 화면이 이 방식이다 | 크기·색이 줄마다 다르면 목록 항목이 복잡해진다 |

**선택: A.** `GAME OVER`는 크게, 그 밑에 점수를 조금 작게 표시하는 화면 구성이라 줄마다 글꼴 크기가 다르다. 줄이 둘뿐이라 직접 호출로 충분하다. `GAME OVER`는 노란색, 점수는 흰색으로 그린다.

#### 결정 5. 동작 명세

- 한 프레임에 적이 여러 마리 닿거나 지나가면 마리당 생명을 1 줄인다.
- 생명이 음수가 될 수 있는 경우(생명 1에서 적 둘이 동시에 닿음)는 0으로 고정한다. 고정은 생명을 잃는 경우를 묶은 상위 메서드가 두 처리를 끝낸 뒤 한 번 한다. 규칙이 한곳에 있어서다. 두 하위 처리 중간에는 생명이 음수일 수 있고, 하위 메서드를 묶음 밖에서 따로 부르면 고정이 되지 않는다는 점은 알고 정했다.

### 4. 구현 단계와 커밋 단위

한 커밋에 한 가지 변경씩 두 단계로 나눈다. 생명 감소와 게임 오버 호출을 먼저 하고, 게임 오버 화면을 뒤에 한다.

1. 생명 감소와 게임 오버 호출 — `feat: 총알로 처리하지 못한 적에 대한 생명 감소, 생명이 0이면 게임 오버 처리`
2. 게임 오버 화면 — `feat: 게임 오버 화면에 GAME OVER 및 점수 표시`

머지는 2단계 커밋까지 끝난 뒤에 한다.

## 이외 고려 사항

- **`groupcollide`나 `colliderect` 직접 비교**: 결정 1에서 고르지 않았다. `groupcollide`는 플레이어만 담긴 그룹이 필요하고 돌려주는 값이 사전이라 구조가 늘어난다. `colliderect`는 반복문과 삭제, 닿은 수 세기를 직접 써야 한다.
- **TODO 세 곳에 직접 작성**: 결정 2에서 고르지 않았다. 과제 모양 그대로지만 생명 감소가 두 곳에 있고 `update`가 길어진다.
- **생명 감소를 메서드 하나로 모으기**: 결정 2에서 고르지 않았다. 규칙이 한곳에 있지만 TODO 세 자리와 모양이 달라진다.
- **상위 묶음 없이 `update`에서 따로 호출, 게임 오버 판정을 묶음 안에 두기**: 결정 2의 하위 결정에서 고르지 않았다. 앞은 층이 하나 적고, 뒤는 호출이 한 줄이지만 묶음이 생명을 잃는 일 밖의 판정까지 맡는다.
- **생명을 깎는 순간마다 게임 오버 검사**: 결정 3에서 고르지 않았다. 한 프레임에 두 번 깎이면 `end_game()`이 두 번 불릴 수 있다.
- **게임 오버 화면을 줄 목록 반복으로 그리기**: 결정 4에서 고르지 않았다. F5에서 줄이 늘 때 편하지만 크기가 다른 두 줄에는 맞지 않는다.
- **0 고정을 깎는 메서드마다 하거나 표시할 때만 하기**: 결정 5에서 고르지 않았다. 메서드마다 하면 같은 규칙이 두 곳에 생기고, 표시할 때만 하면 생명 값과 화면이 달라진다.
- **한 프레임에 최대 1만 깎기, 무적 시간, 피격 효과음·깜빡임, 목숨 추가 아이템**: 과제에 없어서 다루지 않았다.
