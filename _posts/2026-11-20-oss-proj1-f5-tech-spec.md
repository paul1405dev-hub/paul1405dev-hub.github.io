Pygame 종스크롤 슈팅 게임 과제의 마지막 기능(F5, 재시작과 최고 점수)을 구현하기 전에 설계 결정을 정리한 문서다. 구조는 뱅크샐러드 테크 스펙 양식(요약, 배경, 목표, 목표가 아닌 것, 계획, 이외 고려 사항, 마일스톤)을 따랐다. 앞 기능은 [F1 플레이어 이동]({{ site.baseurl }}/2026-11-17-oss-proj1-f1-tech-spec/), [F2 총알 발사]({{ site.baseurl }}/2026-11-17-oss-proj1-f2-tech-spec/), [F3 적 명중과 점수]({{ site.baseurl }}/2026-11-18-oss-proj1-f3-tech-spec/), [F4 피격과 게임 오버]({{ site.baseurl }}/2026-11-19-oss-proj1-f4-tech-spec/) 테크 스펙에 있다.

## 요약

- 최고 점수 갱신 및 게임 재시작 로직, 게임 오버 화면 재배치 및 최고 점수, 재시작 안내 추가.
- 최고 점수는 파일에 저장해 게임을 껐다 켜도 유지한다. 파일을 읽고 쓰는 오류는 종류마다 `print`로 드러내면서 게임이 멈추지 않게 한다.
- 설계 결정 7개를 구현 전에 정하고, 구현은 `feature/restart` 브랜치에서 커밋 2개로 나눈다.

## 배경

- F4까지로 게임이 시작해서 끝나지만 다시 시작할 수 없고, 점수는 판이 끝나면 사라진다. F5는 게임 오버에서 R로 새 판을 시작하게 하고 최고 점수를 파일에 저장하는 마지막 기능이다.
- `load_high_score()`는 게임을 시작할 때 불리므로, 파일이 없거나 내용이 숫자가 아닐 때 오류 없이 0을 돌려줘야 한다. 시작부터 오류가 나면 모든 기능이 채점되지 않는다.
- 이번 과제의 개인 목표는 코드를 많이 쓰는 것보다 구현 전에 설계 선택지와 트레이드오프를 직접 파악하고 선택하는 것이다.

## 목표

- `load_high_score()`: `highscore.txt`에서 최고 점수를 읽어 `int`로 돌려준다. 파일이 없거나 내용이 숫자가 아니면 0을 돌려준다.
- `save_high_score(score)`: 점수를 파일에 저장한다. 다음 실행 때 `load_high_score()`로 읽을 수 있어야 한다.
- `end_game()`: 이번 점수가 최고 점수보다 높을 때만 `self.high_score`를 바꾸고 저장한다.
- `handle_events()`: 게임 오버 상태에서 R 키를 누르면 `self.reset()`으로 새 판을 시작한다.
- `draw_game_over()`: `HIGH SCORE: 300`과 `Press R to restart`를 표시한다. 게임을 껐다 켜도 이전 최고 점수가 보인다.

## 목표가 아닌 것

- 시작 화면에 최고 점수 표시, 점수 순위표, 최고 점수 초기화 기능은 과제에 없어서 다루지 않는다.

## 계획

### 1. 현재 구조 분석

| 대상 | 위치 | 알게 된 것 |
|---|---|---|
| 파일 경로 | `settings.py` | `BASE_DIR = os.path.dirname(os.path.abspath(__file__))`에서 `abspath`는 `settings.py`의 경로를 절대 경로로 바꾸고 `dirname`은 파일 이름을 떼고 폴더 부분만 남긴다. `HIGHSCORE_FILE = os.path.join(BASE_DIR, "highscore.txt")`는 그 폴더 경로에 `highscore.txt`를 운영체제에 맞는 구분자로 이어붙인다. `load_high_score()`와 `save_high_score()`는 모두 이 `HIGHSCORE_FILE`을 통해 파일에 접근한다 |
| 재시작 입력 | `main.py` `handle_events()` | `KEYDOWN` 분기에서 R 키를 누르고 `self.game_over`가 True이면 `self.reset()`을 호출하기만 하면 된다. 이 조건이 없으면 게임 중 R로도 판이 초기화된다 |

### 2. 목표 구조

★은 F5에서 작성하는 부분이다.

```
Game.__init__
 └─ high_score = load_high_score() ★      시작할 때 한 번, 읽을 수 없으면 0

handle_events()
 └─ KEYDOWN, R, game_over ★ → reset()

check_game_over() → end_game()
 └─ update_high_score() ★                 이번 점수가 높을 때만 갱신하고 save_high_score() ★

draw_game_over() ★                        GAME OVER(빨강), Press R to restart(노랑),
                                          점수 줄 목록 SCORE·HIGH SCORE(흰색)
```

### 3. 설계 결정과 트레이드오프

#### 결정 1. 파일을 읽을 때의 오류를 어떻게 처리할 것인가

파일을 읽는 코드에서 생길 수 있는 오류는 파일이 없을 때(`FileNotFoundError`), 내용이 숫자가 아닐 때(`ValueError`), 읽기 권한이 없을 때(`PermissionError`) 등이다. 파일이 없거나 권한이 없는 오류는 `OSError`라는 같은 부모 아래에 있다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `FileNotFoundError`와 `ValueError`만 잡는다 | 예상한 두 경우와 정확히 대응한다 | 권한 문제 같은 다른 오류에서는 시작이 멈춘다 |
| B. `OSError`와 `ValueError`를 잡는다 | 파일 읽기 오류를 한 묶음으로 처리한다 | 파일 없음과 읽기 실패의 구분이 사라진다 |
| C. 파일 유무를 먼저 확인하고 변환만 `try`로 감싼다 | 파일 없음이 사전 검사라 읽기 쉽다 | 확인과 읽기 사이에 상태가 바뀔 수 있고 권한 오류가 남는다 |
| D. 오류 종류마다 `except`를 따로 두고 각각 `print`한 뒤 0으로 시작한다 | 어떤 이유로든 시작이 막히지 않으면서 어떤 경우였는지 드러난다. 상정 외 오류는 "확인 필요"로 찍는다 | `except`가 셋이라 코드가 길고, 처음 실행마다 메시지가 찍힌다 |

**선택: D.** 전부 잡아서 시작은 막히지 않게 하고, 상정한 경우도 각각 어떤 오류인지 `print`로 드러내며, 그 외의 오류는 상정 외 오류라 확인이 필요하다고 찍는다. `except`는 구체적인 것(`FileNotFoundError`, `ValueError`)을 위에, `Exception`을 아래에 둔다.

#### 결정 2. 파일 저장이 실패하면 어떻게 할 것인가

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 처리하지 않는다 | 코드가 가장 단순하다 | 게임 오버 순간 게임이 오류로 멈춘다 |
| B. 잡아서 무시한다 | 저장이 안 돼도 게임은 계속된다 | 저장 실패를 모르고 지나간다 |
| C. 잡고 `print`로 알린다 | 게임은 계속되고 실패는 터미널에 보인다 | `except`가 하나 더 늘어난다 |

**선택: C.** 결정 1과 같은 기준을 적용한다.

#### 결정 3. 최고 점수 갱신을 어디서 할 것인가 (구조 설계)

개념: **단일 책임**. `end_game()`은 게임 오버 처리를 맡고, 최고 점수 갱신(비교, 변경, 저장)은 바뀌는 이유가 다르다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `end_game()` 안에 직접 쓴다 | 과제 모양 그대로이고 한눈에 보인다 | 게임 오버 처리와 최고 점수 갱신이 한 메서드에 섞인다 |
| B. 갱신을 `Game`의 메서드로 분리하고 `end_game()`이 부른다 | `end_game()`은 흐름만 읽힌다. F1~F4와 같은 책임별 분리다 | 메서드가 늘고 두서너 줄이라 얻는 게 작을 수 있다 |

**선택: B.** 책임별로 나누는 기준을 F1~F4와 같이 유지한다.

#### 결정 4. R 키 재시작을 어디서 처리할 것인가 (구조 설계)

`reset()`이 이미 있어서 재시작은 `self.reset()` 한 줄이다. 조건은 게임 오버 상태에서 R이다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `handle_events` 분기에 직접 쓴다 | 과제 TODO 자리 그대로이고 한 줄이다 | 입력 규칙이 분기 안에 늘어난다 |
| B. 재시작을 `Game`의 메서드로 분리하고 분기에서 부른다 | 분기는 R이면 재시작만 말한다 | 한 줄을 한 줄로 감싸서 얻는 게 거의 없다 |

**선택: A.** 앞의 결정들(책임별 분리)과 달리 감쌀 내용이 `self.reset()` 한 줄뿐이라 메서드로 나눠도 얻는 게 없다.

#### 결정 5. 게임 오버 화면의 줄을 어떻게 늘릴 것인가 (구조 설계)

F4에서 줄이 늘면 바꿀 수 있다고 남겨둔 결정이다. `GAME OVER`(큰 글꼴) 다음에 작은 글꼴 줄 셋(`SCORE`, `HIGH SCORE`, `Press R to restart`)이 된다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `draw_text`를 줄마다 직접 호출 | F4에서 쓴 방식 그대로 줄을 더한다 | y 좌표를 줄마다 직접 맞춰야 한다 |
| B. 작은 글꼴 줄을 목록으로 만들어 간격으로 반복 | 줄이 늘어도 목록만 고치면 된다. 시작 화면의 조작 안내가 이 방식이다 | 줄마다 색이 다르면 목록 항목이 복잡해진다 |

**선택: 점수 줄은 B(목록 반복), `Press R to restart`는 A(직접 호출).** 이후 설계를 확장할 때(점수표를 보여주거나 점수끼리 묶을 때) 점수 줄은 목록 반복이 낫다. 재시작 안내는 점수와 성격이 달라서 직접 그린다. 순서는 `GAME OVER`, `Press R to restart`, 점수 줄들이고, 색은 각각 빨강, 노랑, 흰색이다.

#### 결정 6. `highscore.txt`를 저장소에서 어떻게 다룰 것인가

게임을 실행해 최고 점수가 저장되면 프로젝트 폴더에 `highscore.txt`가 생겨 추적 안 된 파일로 계속 보인다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `.gitignore`에 추가해 제외한다 | 실수로 커밋하지 않는다 | `.gitignore`를 건드리는 커밋이 하나 더 필요하다 |
| B. 제외하지 않고 커밋하지 않도록 조심한다 | 추가 작업이 없다 | `git add .`로 실수로 올릴 위험이 있다 |
| C. 커밋한다 | 처음 실행에서도 최고 점수가 보인다 | 내 실행 기록이 저장소에 남고 매번 바뀌는 파일이 추적된다 |

**선택: A.** 제외하고 실수로 커밋하는 것을 막는다. 이 커밋은 브랜치의 마지막 커밋이 구현이어야 해서 머지 뒤 `main`에서 한다.

#### 결정 7. 동작 명세

- 점수가 최고 점수와 같을 때와 게임 오버 화면의 `HIGH SCORE` 값은 따로 명시하지 않는다(과제의 높을 때만 갱신을 따른다).
- 파일에 음수 값이 있으면 0 미만이므로 0으로 본다. `int()`는 음수를 숫자로 읽으므로 읽은 뒤 0 이상으로 맞춘다.

### 4. 구현 단계와 커밋 단위

한 커밋에 한 가지 변경씩 두 단계로 나눈다. 최고 점수 읽기·저장·갱신을 먼저 하고, 재시작과 게임 오버 화면을 뒤에 한다.

1. 최고 점수 읽기·저장·갱신 — `feat: 최고 점수 갱신 로직`
2. 재시작과 게임 오버 화면 — `feat: R 키로 재시작, 게임 오버 화면 재배치 및 최고 점수와 재시작 안내 표시 추가`

머지는 2단계 커밋까지 끝난 뒤에 하고, 머지 뒤 `main`에서 `.gitignore` 커밋(`chore: highscore.txt를 .gitignore에 추가`)을 한다.

## 이외 고려 사항

- **`FileNotFoundError`와 `ValueError`만 잡기, `OSError`와 `ValueError`를 묶어 잡기, 파일 유무를 먼저 확인하기**: 결정 1에서 고르지 않았다. 앞의 둘은 예상한 오류만 처리해 권한 문제 같은 경우에 시작이 멈출 수 있고, 시작 오류는 모든 기능에 영향을 준다. 파일 유무 확인은 확인과 읽기 사이에 상태가 바뀔 수 있다.
- **`except Exception`으로 전부 조용히 삼키기**: 결정 1에서 고르지 않았다. 시작은 막히지 않지만 코드 실수까지 보이지 않는다.
- **저장 실패를 처리하지 않거나 조용히 무시하기**: 결정 2에서 고르지 않았다.
- **최고 점수 갱신을 `end_game()` 안에 직접 작성**: 결정 3에서 고르지 않았다. 게임 오버 처리와 갱신이 한 메서드에 섞인다.
- **재시작을 메서드로 감싸기**: 결정 4에서 고르지 않았다. 감쌀 내용이 한 줄뿐이다.
- **게임 오버 화면의 모든 줄을 직접 호출로, 또는 모든 줄을 목록 반복으로 그리기**: 결정 5에서 고르지 않았다. 직접 호출만 쓰면 점수표 같은 확장 때 y 좌표를 줄마다 맞춰야 하고, 모든 줄을 목록으로 하면 색이 다른 줄 때문에 목록 항목이 복잡해진다.
- **`highscore.txt`를 제외하지 않거나 커밋하기**: 결정 6에서 고르지 않았다.
- **파일의 음수 값을 그대로 읽거나 숫자 아님으로 취급하기**: 결정 7에서 고르지 않았다.
- **시작 화면에 최고 점수 표시, 점수 순위표, 최고 점수 초기화**: 과제에 없어서 다루지 않았다.

## 작성 방식

설계 결정과 선택은 내가 했고, 선택지·개념 설명과 구현 코드, 이 문서의 문장 정리는 AI(Claude Code)의 도움을 받았다.
