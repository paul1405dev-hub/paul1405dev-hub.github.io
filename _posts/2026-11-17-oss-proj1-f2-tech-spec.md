Pygame 종스크롤 슈팅 게임 과제의 두 번째 기능(F2, 총알 발사)을 구현하기 전에 설계 결정을 정리한 문서다. 구조는 뱅크샐러드 테크 스펙 양식(요약, 배경, 목표, 목표가 아닌 것, 계획, 이외 고려 사항, 마일스톤)을 따랐다. 첫 기능은 [F1 플레이어 이동 테크 스펙]({{ site.baseurl }}/2026-11-17-oss-proj1-f1-tech-spec/)에 있다.

## 요약

- 스페이스바 입력을 받아 총알을 발사하는 로직. 입력 한 번에 총알 한 개가 나가며 화면을 벗어나면 사라짐.
- 발사 입력 연결(`main.py`)과 총알 생성·이동·제거(`entities.py`)를 나누어 구현한다. 총알을 만드는 일, 그룹에 등록하는 일, 없애는 일의 담당을 구현 전에 정한다.
- 설계 결정 6개를 구현 전에 정하고, 구현은 `feature/bullet` 브랜치에서 커밋 2개로 나눈다.

## 배경

- F1로 플레이어가 움직이게 됐지만 아직 공격 수단이 없다. F3(총알과 적 충돌)이 `self.bullets` 그룹을 쓰므로 F2가 먼저 필요하다.
- F2는 `TODO(F2)` 세 곳(`Player.shoot`, `Bullet.update`, `main.py`의 `handle_events`)을 채우는 기능이다. F2와 F5가 `handle_events`를, F3과 F4가 `update`를 함께 건드려서 F2 브랜치는 F1을 머지한 `main`에서 만들었다.
- 이번 과제의 개인 목표는 코드를 많이 쓰는 것보다 구현 전에 설계 선택지와 트레이드오프를 직접 파악하고 선택하는 것이다.

## 목표

- `Player.shoot()`: 플레이어 위쪽 가운데에서 `Bullet(x, y)`를 만들어 반환한다. x는 플레이어의 가로 가운데, y는 플레이어의 위쪽 끝이다.
- `Bullet.update()`: 매 프레임 `BULLET_SPEED`만큼 위로 움직이고, 화면 위로 완전히 나가면 `self.kill()`로 없앤다.
- `handle_events()`: 스페이스를 누르면 `self.player.shoot()`이 돌려준 총알을 `self.bullets`와 `self.all_sprites` 두 그룹에 넣는다. 게임 오버 중에는 쏘지 않는다.
- 시작 화면에서 스페이스로 게임을 시작할 때 총알이 같이 나가지 않고, 시작부터 오류가 없다.

## 목표가 아닌 것

- 총알과 적 충돌·점수(F3), 피격·게임 오버(F4), 재시작·최고 점수(F5)는 이 문서의 범위가 아니다.
- 발사음, 총알 종류, 탄약 제한처럼 과제에 없는 기능은 다루지 않는다.

## 계획

### 1. 현재 구조 분석

스타터 코드에서 F2와 관련된 부분만 추렸다.

| 대상 | 위치 | 알게 된 것 |
|---|---|---|
| `Player.shoot()` | `entities.py` | 본문이 `return None`이다. TODO에 x는 플레이어의 가로 가운데, y는 위쪽 끝이라고 적혀 있다 |
| `Bullet.__init__` | `entities.py` | 이미 있다. 그림을 불러오고 `rect`를 `midbottom=(x, y)`에 놓는다. `shoot()`은 x, y만 정해서 넘기면 된다 |
| `Bullet.update()` | `entities.py` | 본문이 `pass`다 |
| 속도 상수 | `settings.py` | `BULLET_SPEED = 10`. `entities.py`가 이미 import하고 있다 |
| 이벤트 처리 | `main.py` `handle_events()` | `pygame.event.get()`으로 한 프레임 사이에 쌓인 이벤트를 모두 받아 종류별로 처리한다. 종료(`QUIT`), 시작 화면 입력, 적 생성, 키 입력(`KEYDOWN`) 순서의 분기가 있고, `KEYDOWN` 분기에 F2 자리가 비어 있다 |
| 시작 화면 | `main.py` | 시작 화면이면 이벤트를 `handle_title_event`가 가져간다. 시작할 때 누른 스페이스는 발사로 넘어오지 않는다 |
| 그룹 갱신 | `main.py` `update()` | `self.bullets.update()`를 매 프레임 부른다. 그룹의 `update()`는 안에 든 스프라이트 각각의 `update()`를 한 번씩 부른다 |
| 게임 오버 | `main.py` | `self.game_over`다. 적 생성 분기가 `not self.game_over`로 같은 방식으로 막고 있다 |
| 키 입력 방식 | `main.py` | 이동은 `get_pressed()`(눌려 있는 동안 매 프레임 참), ESC와 시작 화면 스페이스는 `KEYDOWN` 이벤트(누른 순간 한 번)로 읽는다 |

### 2. 목표 구조

총알 한 발이 도는 흐름이다. ★은 F2에서 작성하는 부분이다.

```
handle_events()                            (main.py)
 └─ KEYDOWN, 스페이스, 게임 오버 아님 ★
     └─ fire() ★                           총알을 받아 두 그룹에 등록
         ├─ player.shoot() ★               (entities.py) Bullet(x, y)를 만들어 반환
         ├─ bullets.add(bullet)
         └─ all_sprites.add(bullet)

update()                                   매 프레임
 └─ bullets.update()                       그룹 안 각 총알의 update()를 부른다
     └─ Bullet.update() ★                  위로 이동, 화면 위로 나가면 kill()
```

- `Bullet(x, y)`를 쓰는 순간 `Bullet.__init__`이 자동으로 한 번 실행되어 그림과 처음 위치가 정해진다. 이후에는 `update`만 매 프레임 불린다.
- `kill()`은 총알이 속한 모든 그룹에서 총알을 뺀다. 그래서 `bullets`(갱신·충돌 판정용)와 `all_sprites`(그리기용)에서 함께 사라진다.

### 3. 설계 결정과 트레이드오프

#### 결정 1. 발사 입력을 어떻게 받을 것인가

개념: **이벤트 큐**(눌린 순간 한 번 알려준다)와 **상태 조회**(지금 눌려 있는지 매 프레임 확인한다)의 차이.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `KEYDOWN`: 한 번 누름 = 한 발 | 코드가 가장 단순하고 TODO의 자리(`handle_events`)에 그대로 들어간다 | 연타해야 하고 연타 속도가 발사 속도다 |
| B. `get_pressed()`: 누르는 동안 연속 발사 | 누르고 있으면 되어 편하다 | 매 프레임 발사하게 되어 발사 간격 제한(결정 2)이 따라와야 하고, 입력 처리가 `handle_events`가 아니라 `update` 쪽으로 간다 |

**선택: A.** TODO가 적힌 자리(`handle_events`의 `KEYDOWN` 분기) 그대로 구현할 수 있다.

#### 결정 2. 발사 간격을 제한할 것인가

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 제한 없음 | 추가 코드가 없다 | 연속 발사(결정 1의 B)와 같이 쓰면 총알이 매 프레임 나온다 |
| B. 프레임 카운터 | 시계 함수를 몰라도 된다 | 프레임 속도(FPS)가 바뀌면 간격도 바뀐다 |
| C. `get_ticks()`로 마지막 발사 시각 비교 | 실제 시간 기준이라 FPS와 무관하다 | 마지막 발사 시각을 저장할 곳이 필요하다 |

**선택: A(제한 없음).** 결정 1에서 `KEYDOWN`을 골라서 발사 속도의 한계가 사람의 연타 속도로 정해진다.

#### 결정 3. 화면 밖으로 나간 총알을 어디서 없앨 것인가 (구조 설계)

개념: **책임**(수명 관리를 누가 맡는가)과 **응집도**(총알에 관한 규칙이 한곳에 있는가). 판단 기준은 소멸 여부를 판단하는 데 필요한 정보를 누가 갖고 있는가다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `Bullet.update()` 안에서 스스로 `kill()` | 이동과 소멸 규칙이 `Bullet` 한 메서드에 모인다. 위쪽 끝을 지났는지는 총알 자신의 `rect`만 보면 된다. 총알 종류가 늘어 소멸 규칙이 달라져도 `Game`이 바뀌지 않는다 | 소멸 조건이 `Game`만 아는 값(점수, 생명, 전체 개체 수)에 걸리면 `Bullet`이 그 값을 알아야 해서 맞지 않는다 |
| B. `Game.update()`에서 일괄 정리 | 적의 화면 이탈 처리와 모양이 같아 `Game.update()`에서 일관되게 읽힌다. 모든 개체에 같은 정리 규칙을 적용할 때 한곳에 모으기 쉽다 | 이동은 `Bullet`, 소멸은 `Game`으로 책임이 나뉜다. 총알을 바꿀 때 `Game`도 같이 봐야 한다 |

이 과제의 총알은 위로 직진하다 위쪽 끝에서 사라지는 것이 전부이고, 소멸 판단에 필요한 정보는 총알의 `rect`뿐이다.

**선택: A.** TODO 문구가 `Bullet.update()` 안에서 `kill()`하라고 적고 있다.

#### 결정 4. 총알을 만드는 일과 그룹에 넣는 일을 누가 할 것인가 (구조 설계)

개념: **결합도**(한 코드가 다른 코드의 세부를 얼마나 아는가)와 **단일 책임**. TODO는 `shoot()`이 총알을 반환하고 `Game`이 그룹에 넣는 모양으로 적혀 있다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `shoot()`은 만들어 반환만 하고, 그룹 추가는 `Game`이 한다 | `Player`가 `Game`의 그룹 구조를 몰라도 된다 | `Game`이 `shoot()`을 부를 때마다 등록 코드를 알아야 한다 |
| B. `Player`가 그룹을 받아 `shoot()` 안에서 직접 추가한다 | 호출하는 쪽이 한 줄이다 | `Player`가 `Game`의 그룹 구조에 묶이고 `shoot()`의 시그니처가 TODO와 달라진다 |

**선택: A.** 설계 측면에서도 `shoot()`은 만들어서 반환만 하고 그룹 추가는 `Game`이 하는 편이 책임이 분리되어 더 좋아 보인다. TODO 모양과도 같다.

#### 결정 5. 발사 처리를 메서드로 나눌 것인가 (구조 설계)

개념: **관심사 분리**(입력이 눌렸는지, 총알을 어디서 만드는지, 목록에 넣는 일을 나눈다).

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `handle_events`의 `KEYDOWN` 분기 안에 직접 쓴다 | 한눈에 보인다 | 키가 더 늘면 분기가 길어지고 입력 규칙과 등록 로직이 한곳에 섞인다 |
| B. `Game`에 발사 메서드를 따로 둔다 | `handle_events`는 스페이스면 발사한다만 말하고, 등록은 이름 붙은 메서드가 맡는다 | 등록 코드가 세 줄이라 메서드와 호출이 늘어 얻는 게 작다 |

**선택: B.** 책임별로 나누는 기준을 F1과 같이 유지한다. 이득이 작다는 점은 알고 정했다.

하위 결정으로 게임 오버 검사는 분기 조건(`K_SPACE and not self.game_over`)에 둔다. 적 생성 분기가 `not self.game_over`를 조건에 두는 방식과 같고, 발사 메서드는 등록하는 일만 맡는다. 검사를 발사 메서드 안에 두면 어디서 불려도 안전해지지만 그 메서드가 조건 확인과 등록 두 일을 맡게 된다.

#### 결정 6. 동작 명세

과제에 규칙이 없는 동작은 정할 것이 없었다. 게임 오버 중에는 쏘지 않는다(과제에 명시). 총알 개수와 발사 간격은 제한하지 않는다(결정 2).

### 4. 구현 단계와 커밋 단위

한 커밋에 한 가지 변경씩 두 단계로 나눈다. 입력 연결을 먼저 하고, 총알이 만들어져 움직이는 부분을 뒤에 한다.

1. 입력 연결 — `feat: 스페이스 입력으로 총알 발사 처리 연결`
2. 총알 생성과 이동 — `feat: 총알 생성과 위로 이동 및 화면 밖 제거 구현`

머지는 2단계 커밋까지 끝난 뒤에 한다.

## 이외 고려 사항

- **누르는 동안 연속 발사**: 결정 1에서 고르지 않았다. 매 프레임 확인하는 곳에 코드를 두어야 하고 TODO가 적힌 자리와 달라진다. 발사 간격 제한이 따라붙는다.
- **발사 간격 제한(프레임 카운터, 시각 비교)**: 결정 2에서 두지 않았다. `KEYDOWN` 방식이라 연타 속도가 발사 속도의 한계가 된다. 마지막 발사 시각이나 남은 프레임을 저장할 곳(`Player` 또는 `Game`)을 정해야 하는 비용도 있다.
- **화면 밖 총알을 `Game.update()`에서 일괄 정리**: 결정 3에서 고르지 않았다. 적의 화면 이탈 처리와 모양이 같아지지만 총알의 소멸 규칙이 `Bullet` 밖으로 나가 책임이 나뉜다.
- **`Player`가 그룹을 받아 `shoot()` 안에서 직접 추가**: 결정 4에서 고르지 않았다. 호출하는 쪽은 한 줄이 되지만 `Player`가 `Game`의 그룹 구조에 묶인다.
- **`handle_events` 분기 안에 발사 코드를 직접 작성**: 결정 5에서 고르지 않았다. 한눈에 보이지만 키가 늘면 분기가 길어진다.
- **총알 개수 제한, 발사음, 총알 종류**: 과제에 없어서 다루지 않았다.

## 작성 방식

설계 결정과 선택은 내가 했고, 선택지·개념 설명과 구현 코드, 이 문서의 문장 정리는 AI(Claude Code)의 도움을 받았다.
