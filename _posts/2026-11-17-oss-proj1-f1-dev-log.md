Pygame 종스크롤 슈팅 게임 과제의 첫 기능(F1, 플레이어 좌우 이동)을 구현하기 전에 설계 결정을 먼저 정리하고, 그 결정대로 두 커밋으로 나눠 구현해 `main`에 머지했다. 이 글은 그 과정을 기술 문서 형식으로 정리한 개발 일지다. 결정별 선택지와 트레이드오프는 [F1 테크 스펙]({{ site.baseurl }}/2026-11-17-oss-proj1-f1-tech-spec/)에 따로 있다.

## 요약

- 방향키(←/→)를 누르는 동안 플레이어가 좌우로 움직이고, 화면 좌우 끝 밖으로 나가지 않게 한다.
- 구현은 `Player.update(keys)` 안에서 세 단계(입력 해석 → 이동 → 경계 보정)로 나누고, 단계마다 메서드 하나가 책임 하나만 맡게 설계했다.
- 설계 결정 5개를 구현 전에 정했고, 구현은 `feature/move` 브랜치에서 커밋 2개로 나눠 `--no-ff`로 머지했다.

## 배경

- 과제는 스타터 코드가 주어진 Pygame 종스크롤 슈팅 게임이다. 기능 5개(F1~F5)를 `TODO(F1)`~`TODO(F5)` 자리에 채우고, 기능마다 `feature/<이름>` 브랜치로 작업해 `main`에 `--no-ff`로 머지하는 Git 규칙이 함께 평가된다.
- F1의 대상은 `entities.py`의 `Player.update(keys)`이고 본문이 비어 있는 상태(`pass`)로 주어졌다.
- 이번 과제의 개인 목표는 코드를 많이 쓰는 것보다 **구현 전에 설계 선택지와 트레이드오프를 직접 파악하고 선택하는 것**이다. 코드 작성은 AI의 도움을 받았고(아래 "작업 방식" 참고), 설계 결정은 내가 했다.

## 목표

- ←를 누르는 동안 `PLAYER_SPEED`만큼 왼쪽으로, →를 누르는 동안 오른쪽으로 계속 움직인다.
- 화면 왼쪽·오른쪽 끝에서 방향키를 계속 눌러도 그림이 화면 밖으로 조금도 나가지 않는다.
- 시작 화면에서 SPACE로 게임을 시작한 뒤 위 동작이 되고, 시작부터 오류가 없다.

## 목표가 아닌 것

- 총알 발사(F2), 적 명중·점수(F3), 피격·게임 오버(F4), 재시작·최고 점수(F5)는 이 문서의 범위가 아니다.
- 상하 이동이나 스프라이트 교체처럼 과제에 없는 기능은 다루지 않는다.

## 계획 — 아키텍처 설계

### 1. 현재 구조 분석

스타터 코드에서 F1과 관련된 부분만 추렸다.

| 대상 | 위치 | 알게 된 것 |
|---|---|---|
| 프레임 루프 | `main.py` `step()` | 한 프레임은 `handle_events → update → draw` 순서로 실행된다 |
| `keys`의 출처 | `main.py` `update()` | `self.player.update(pygame.key.get_pressed())`로 매 프레임 한 번 넘어온다. `Player`가 직접 만들지 않는다 |
| 위치 저장 | `entities.py` `Player.__init__` | `Sprite`를 상속하고 `self.image`와 `self.rect`를 직접 채운다. `rect`가 그리는 위치와 판정 영역을 겸한다 |
| 상수 | `settings.py` | `PLAYER_SPEED = 6`, `WIDTH = 480`, `HEIGHT = 640`. `entities.py`가 이미 import하고 있다 |
| 상태 처리 | `main.py` `update()` | 시작 화면(`on_title`)과 게임 오버(`game_over`)에서는 `Player.update` 호출 전에 `return`한다 |

### 2. 목표 구조

`Player.update`는 흐름만 말하고, 세부는 이름이 붙은 메서드가 하나씩 맡는다.

```
Game.step()                              (main.py)
 ├─ handle_events()
 ├─ update()
 │   └─ player.update(keys)              keys = pygame.key.get_pressed()
 │        ├─ _read_direction(keys)  →  -1 / 0 / +1        입력 해석
 │        ├─ _move(direction)       →  rect.x 이동         이동
 │        └─ _keep_in_screen()      →  left ≥ 0, right ≤ WIDTH   경계 보정
 └─ draw()
```

- 입력 해석(`_read_direction`)만 `keys`를 안다. 이동(`_move`)은 방향 값(-1, 0, +1)만 받으므로 입력이 키보드인지 모른다.
- 경계 보정(`_keep_in_screen`)은 `rect`와 `WIDTH`만 본다.
- 스타터가 정한 `update(keys)` 시그니처와 `main.py`의 호출은 그대로 둔다.

### 3. 설계 결정과 트레이드오프

| # | 질문 | 선택 | 핵심 이유 |
|---|---|---|---|
| 1 | 경계를 어떻게 판정·제한할까 | 먼저 이동하고, 넘어갔으면 끝에 맞춰 되돌린다 | 끝과 간격이 남는 게 싫다. 한 프레임 안에서 이동과 보정이 연달아 실행되고 그 사이에 그리는 코드가 없어 밖으로 나간 위치는 화면에 보이지 않는다 |
| 2 | ←와 →를 동시에 누르면 | 움직이지 않는다 | 대부분의 게임이 그렇게 처리하고 유저가 느끼기에도 합당해 보인다 |
| 3 | 움직이면 안 되는 상태가 있나 | `Player.update`에 따로 막지 않는다 | 시작 화면·게임 오버는 스타터가 이미 `Player.update` 호출 전에 처리한다 |
| 4 | 이동·경계 코드를 어디에 둘까 | `Player` 안에서 책임별 메서드로 분리한다 | 이동과 경계 보정은 바뀌는 이유가 달라 나누는 편이 수정하기 쉽고 단일 책임 원칙에 맞는다 |
| 5 | `keys` 해석을 어디서 할까 | 별도 메서드로 해석하고, 이동은 방향 값만 받는다 | 비용이 작고 입력이 어디서 오든 이동은 방향 값만 받으면 된다(결합도가 낮아진다) |

선택지별 장단점은 [테크 스펙]({{ site.baseurl }}/2026-11-17-oss-proj1-f1-tech-spec/)에 있다.

### 4. 이 설계에서 쓴 개념

- **단일 책임 원칙(SRP)**: 한 덩어리는 바뀌는 이유가 하나여야 한다. 키 배치, 속도, 경계 규칙, 화면 크기가 서로 다른 이유로 바뀐다고 보고 이동과 경계를 갈랐다.
- **결합도**: 한 코드가 다른 코드의 세부를 얼마나 아는가. `_move`가 `keys`를 모르게 해서 낮췄다.
- **관심사 분리**: "눌린 키가 무엇인가"를 아는 일과 "얼마나 움직이는가"를 아는 일을 나눴다.
- 한계도 확인했다. F1은 코드가 열 줄 안팎이라 이 분리의 이득이 크게 드러나지 않는다. 책임 분리가 값을 하는 건 `update`에 일이 더 붙는 F2~F4부터라고 본다.

## 이외 고려 사항

- 경계 판정을 이동 전에 검사하는 방식: 남은 거리가 속도(6)보다 작으면 끝과 간격이 남을 수 있어 채택하지 않았다.
- `pygame.Rect`의 보정 메서드로 가두는 방식: 코드는 짧아지지만 사용법을 새로 익혀야 했고, 이번에는 익숙한 방식을 골랐다. 나중에 공부할 항목으로 남겼다.
- `Player.update` 안에 전부 쓰는 방식: 바뀌는 이유가 한 함수에 섞여 채택하지 않았다.
- `Game`(`main.py`)이 `rect`를 직접 움직이는 방식: 스타터가 `TODO(F1)`를 `Player.update` 안에 둔 구조와 어긋나 채택하지 않았다.
- `keys`를 이동 메서드가 직접 읽는 방식: 입력이 바뀌면 이동 메서드까지 고쳐야 해서 채택하지 않았다.

## 구현과 검증

구현은 한 커밋에 한 가지 변경만 담도록 두 단계로 나눴다.

| 단계 | 내용 | 커밋 |
|---|---|---|
| 1 | 입력 해석 + 이동 | `542fe95` `feat : 방향키 입력으로 플레이어 좌우 이동 구현` |
| 2 | 경계 보정 | `a7afcbd` `feat: 플레이어가 화면 좌우 끝을 벗어나지 않게 제한` |

두 커밋 뒤 `feature/move`를 `main`에 `--no-ff`로 머지했다(`27590e8`, 2026-11-17).

최종 `Player`는 다음과 같다.

```python
class Player(pygame.sprite.Sprite):
    def update(self, keys):
        direction = self._read_direction(keys)
        self._move(direction)
        self._keep_in_screen()

    def _read_direction(self, keys):
        """왼쪽 -1, 정지 0, 오른쪽 +1. 둘 다 누르면 0."""
        return keys[pygame.K_RIGHT] - keys[pygame.K_LEFT]

    def _move(self, direction):
        self.rect.x += direction * PLAYER_SPEED

    def _keep_in_screen(self):
        if self.rect.left < 0:
            self.rect.left = 0
        if self.rect.right > WIDTH:
            self.rect.right = WIDTH
```

검증은 창 없이 가짜 키 입력으로 `Player.update`를 직접 호출해서 했다.

- 왼쪽만 누르면 -6, 오른쪽만 누르면 +6, 둘 다 누르면 0, 아무것도 안 누르면 0
- 왼쪽·오른쪽을 200프레임씩 누르면 `left`는 0, `right`는 480(`WIDTH`)에서 멈추고 그 범위를 넘은 적이 없다
- 끝에서 반대 방향으로 한 번 누르면 6만큼 되돌아와 끝에 갇히지 않는다
- 실제 창에서 키를 눌러 확인하는 것은 직접 실행으로 따로 한다

## 작업 방식

- 설계 결정과 트레이드오프 선택, 커밋·브랜치·머지는 내가 직접 했다.
- 선택지와 개념 설명, 구현 코드는 AI(Claude Code)의 도움을 받았고 `AI_USAGE.md`에 기록했다. 코드는 수정 없이 반영했다.
- 이 글과 테크 스펙의 문장 정리도 AI의 도움을 받았다.
