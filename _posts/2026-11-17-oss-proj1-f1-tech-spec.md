Pygame 종스크롤 슈팅 게임 과제의 첫 기능(F1, 플레이어 좌우 이동)을 구현하기 전에 설계 결정을 정리한 문서다. 구조는 뱅크샐러드 테크 스펙 양식(요약, 배경, 목표, 목표가 아닌 것, 계획, 이외 고려 사항, 마일스톤)을 따랐다.

## 요약

- 방향키(←/→)를 누르는 동안 플레이어가 좌우로 움직이고, 화면 좌우 끝 밖으로 나가지 않게 한다.
- `Player.update(keys)` 안에서 세 단계(입력 해석 → 이동 → 경계 보정)로 나누고, 단계마다 메서드 하나가 책임 하나만 맡게 설계한다.
- 설계 결정 5개를 구현 전에 정하고, 구현은 `feature/move` 브랜치에서 커밋 2개로 나눈다.

## 배경

- 과제는 스타터 코드가 주어진 Pygame 종스크롤 슈팅 게임이다. 기능 5개(F1~F5)를 `TODO(F1)`~`TODO(F5)` 자리에 채우고, 기능마다 `feature/<이름>` 브랜치로 작업해 `main`에 `--no-ff`로 머지하는 Git 규칙이 함께 평가된다.
- F1의 대상은 `entities.py`의 `Player.update(keys)`이고, 본문이 비어 있는 상태(`pass`)로 주어졌다.
- 이번 과제의 개인 목표는 코드를 많이 쓰는 것보다 구현 전에 설계 선택지와 트레이드오프를 직접 파악하고 선택하는 것이다.

## 목표

- ←를 누르는 동안 `PLAYER_SPEED`만큼 왼쪽으로, →를 누르는 동안 오른쪽으로 계속 움직인다.
- 화면 왼쪽·오른쪽 끝에서 방향키를 계속 눌러도 그림이 화면 밖으로 조금도 나가지 않는다.
- 시작 화면에서 SPACE로 게임을 시작한 뒤 위 동작이 되고, 시작부터 오류가 없다.

## 목표가 아닌 것

- 총알 발사(F2), 적 명중·점수(F3), 피격·게임 오버(F4), 재시작·최고 점수(F5)는 이 문서의 범위가 아니다.
- 상하 이동이나 스프라이트 교체처럼 과제에 없는 기능은 다루지 않는다.

## 계획

### 1. 현재 구조 분석

스타터 코드에서 F1과 관련된 부분만 추렸다.

| 대상 | 위치 | 알게 된 것 |
|---|---|---|
| 프레임 루프 | `main.py` `step()` | 한 프레임은 `handle_events → update → draw` 순서로 실행된다 |
| `keys`의 출처 | `main.py` `update()` | `self.player.update(pygame.key.get_pressed())`로 매 프레임 한 번 넘어온다. `Player`가 직접 만들지 않는다 |
| 위치 저장 | `entities.py` `Player.__init__` | `Sprite`를 상속하고 `self.image`와 `self.rect`를 직접 채운다. `rect`가 그리는 위치와 판정 영역을 겸한다 |
| 상수 | `settings.py` | `PLAYER_SPEED = 6`, `WIDTH = 480`, `HEIGHT = 640`. `entities.py`가 이미 import하고 있다 |
| 상태 처리 | `main.py` `update()` | 시작 화면(`on_title`)과 게임 오버(`game_over`)에서는 `Player.update` 호출 전에 `return`한다 |

### 2. 목표 구조

`Player.update`는 흐름만 말하고, 세부는 이름이 붙은 메서드가 하나씩 맡는다.

```
Game.step()                              (main.py)
 ├─ handle_events()
 ├─ update()
 │   └─ player.update(keys)              keys = pygame.key.get_pressed()
 │        ├─ _read_direction(keys)  →  -1 / 0 / +1        입력 해석
 │        ├─ _move(direction)       →  rect.x 이동         이동
 │        └─ _keep_in_screen()      →  left ≥ 0, right ≤ WIDTH   경계 보정
 └─ draw()
```

- 입력 해석(`_read_direction`)만 `keys`를 안다. 이동(`_move`)은 방향 값(-1, 0, +1)만 받으므로 입력이 키보드인지 모른다.
- 경계 보정(`_keep_in_screen`)은 `rect`와 `WIDTH`만 본다.
- 스타터가 정한 `update(keys)` 시그니처와 `main.py`의 호출은 그대로 둔다.

### 3. 설계 결정과 트레이드오프

#### 결정 1. 경계를 어떻게 판정하고 제한할 것인가

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 먼저 움직이고 넘어갔으면 끝에 맞춰 되돌린다 | 항상 끝에 딱 붙어 멈춘다 | 이동·보정 두 단계라 보정 줄을 빠뜨리면 밖으로 나간다 |
| B. 이동 전에 검사해 넘어갈 것 같으면 안 움직인다 | 위치가 밖으로 나간 적이 없다 | 남은 거리가 속도(6)보다 작으면 끝과 간격이 남을 수 있다 |
| C. `pygame.Rect`의 보정 메서드를 쓴다 | 비교하는 줄이 줄어든다 | 사용법을 새로 익혀야 하고 화면 영역 `Rect`를 따로 만들어야 한다 |

**선택: A.** 끝과 간격이 남는 걸 원하지 않는다. 한 프레임이 `handle_events → update → draw` 순서로 실행되고, 이동과 보정이 같은 `Player.update` 안에서 연달아 실행되어 그 사이에 그리는 코드가 없다. 그래서 밖으로 나간 위치는 어떤 화면에도 그려지지 않고, `update` 뒤의 충돌 판정(F3·F4)도 보정된 위치만 본다. C는 사용법을 공부할 시간이 부담돼 익숙한 A를 골랐다.

#### 결정 2. ←와 →를 동시에 누르면 어떻게 할 것인가

과제에 규칙이 없는 동작 명세 결정이라 선택지 비교는 두지 않았다. **선택: 움직이지 않는다.** 대부분의 게임이 동시 입력을 이렇게 처리하고 유저가 느끼기에도 합당해 보인다.

#### 결정 3. 움직이면 안 되는 상태가 있는가

`main.py`의 상태 플래그는 `on_title`(시작 화면)과 `game_over` 둘뿐이고, 둘 다 `Player.update` 호출 전에 `return`한다. **선택:** `Player.update`에 상태 검사를 따로 넣지 않는다. 스타터가 이미 처리하고 있다.

#### 결정 4. 이동·경계 처리 코드를 어디에 둘 것인가 (구조 설계)

개념: **책임**(그 코드가 맡은 일)과 **단일 책임 원칙(SRP)**(한 덩어리는 바뀌는 이유가 하나여야 한다). 키 배치, 속도, 경계 규칙, 화면 크기는 서로 다른 이유로 바뀐다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `Player.update` 안에 전부 | 열 줄 안팎이라 한눈에 보이고 새 이름이 필요 없다 | 바뀌는 이유가 한 함수에 섞여 규모가 커지면 읽기 어렵다 |
| B. `Player` 안에서 메서드로 분리 | `update`는 흐름만 읽히고 경계 규칙만 따로 고치기 쉽다 | 열 줄짜리에 이름과 호출이 늘어 얻는 게 작을 수 있다 |
| C. `Game`이 `player.rect`를 직접 움직임 | `Player`가 입력과 화면 크기를 몰라도 된다 | 위치를 가진 객체 바깥에서 값을 바꿔 상태 변경이 흩어지고, 스타터가 `TODO(F1)`를 `Player.update`에 둔 구조와 어긋난다 |

**선택: B.** 책임별(이동 / 경계 보정)로 나누면 수정하기 편하고 단일 책임 원칙에 맞는다. 입력 방향별(왼쪽 / 오른쪽)은 코드가 거의 같아 중복만 늘어서 쓰지 않았다. 메서드 하나는 책임 하나만 맡는다.

#### 결정 5. `keys`를 해석하는 일을 어디서 할 것인가 (구조 설계)

개념: **결합도**(한 코드가 다른 코드의 세부를 얼마나 아는가)와 **관심사 분리**(눌린 키를 아는 일과 얼마나 움직이는지 아는 일을 나눈다). 전제는 결정 4의 B이고, `main.py`의 `update(keys)` 호출과 시그니처는 유지한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 이동 메서드가 `keys`를 직접 읽는다 | 단계가 적어 코드가 짧다 | 이동이 키보드를 알게 되고 결정 2의 규칙이 이동 안 조건 분기로 들어간다 |
| B. 입력 해석을 별도 메서드로 두고 이동은 방향 값만 받는다 | 이동이 입력 장치를 모르고 결정 2의 규칙이 해석 한 곳에 모인다 | 책임이 셋(입력 해석·이동·경계 보정)이 되어 이름과 호출이 늘고, 입력이 키보드뿐이면 이득이 작다 |

**선택: B.** 메서드 하나를 더 나누는 비용이 작고, 이후 입력이 어디서 오든 이동 메서드는 방향 값만 받으면 된다.

### 4. 구현 단계와 커밋 단위

한 커밋에 한 가지 변경씩 두 단계로 나눈다.

1. 이동(입력 해석 메서드 포함) — `feat: 방향키 입력으로 플레이어 좌우 이동 구현`
2. 경계 보정 — `feat: 플레이어가 화면 좌우 끝을 벗어나지 않게 제한`

머지는 2단계 커밋까지 끝난 뒤에 한다.

## 이외 고려 사항

- F1은 코드가 열 줄 안팎이라 메서드 분리(결정 4, 5)의 이득이 크게 드러나지 않는다. 책임 분리가 값을 하는 건 `update`에 일이 더 붙는 F2~F4부터라고 본다.
- 결정 1에서 쓰지 않은 `pygame.Rect`의 보정 메서드(`clamp_ip` 등)는 나중에 공부할 항목으로 남긴다.
